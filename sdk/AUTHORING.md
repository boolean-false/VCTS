# Как организовать большой проект

Пишите на TypeScript, разделяя программу по ответственности. Модули объявляют
контракты через exports; runtime-импорты образуют направленный граф без циклов.
Не делайте один файл с глобальным состоянием и всеми обработчиками.

## Структура

Для готового чужого пака используйте `vcts add <pack-folder>` и импорт по ID
`import * as api from "pack:api"`. Его Lua-код не входит в вашу сборку.
Если типов нет, `vcts types <pack-folder>` создаёт ручной контракт; заполните его
по реальному API. Подробный порядок подключения описан в `VCTS_GUIDE.md`, который
поставляется в корне нового проекта. Во время теста зависимости подключаются
во временном проекте; их установленные файлы не меняются.

Начните с шаблона `vcts init`. Оставляйте инфраструктуру в `lib/`, модель предметной
области — в отдельных модулях, а `world.ts`, компоненты и layout — точками сборки.
Сначала определите входные данные, типы состояния и события подсистемы. Затем
реализуйте её. Межпаковый public API экспортируйте из нескольких небольших файлов;
в `packs.public` указываются пути с `.ts`, в require сборщик использует путь без него.

Типы межмодульных контрактов импортируйте через `import type`. Это не создаёт
runtime-зависимость. Взаимные runtime-импорты запрещены, потому что загрузчик VC
не защищает загрузку незавершённого модуля. Лучше передать зависимость параметром
фабрики либо разделить общий контракт и реализацию.

`vcts inspect config.json pack:module` показывает конкретный модуль: путь, imports,
exports и сигнатуры. Для нейросети это удобная точка начала работы: прочитать
контракт нужной подсистемы и её зависимости, затем только соответствующие тела
функций. Не нужно каждый раз включать весь SDK или все исходники проекта в контекст.
После изменения запускайте `check`, затем тест относящегося к изменению сценария.

## Состояние и lifetime

Импортированный TS-модуль кешируется внутри Lua-состояния. Фабрика компонента
выполняется для каждой сущности; фабрика layout — для каждого документа. Держите
изменяемое состояние экземпляра в замыкании фабрики. В конструкторе модуля оставляйте
типы, константы и функции. Генератор работает в отдельном Lua-состоянии, с явным
`GeneratorContext`; его нельзя использовать как хранилище общего состояния игры.

`Scope` владеет подписками, таймерами и произвольной очисткой. Освобождение идёт в
обратном порядке, повторные вызовы безопасны. Если одна очистка бросает ошибку,
остальные всё равно выполняются, затем ошибка передаётся вызывающему коду.
Связывайте scope с `on_world_quit`, `on_destroy` layout или `on_despawn` компонента.
Не путайте временную остановку сущности с уничтожением: on_disable не всегда
означает конец её жизни.

`EventBus<{damage:[target:number,amount:number]}>` задаёт типы имён и payload.
Это собственная шина программы. `events` VC остаётся динамическим API; при
подключении внешнего события проверяйте payload на границе. Scope удаляет слушателя
при завершении владельца. Новая подписка во время emit вступает со следующего
emit; удалённый слушатель пропускается сразу.

## Время и async

`Scheduler.tick(seconds)` продвигает часы. `after` запускает один раз, `every`
повторяется. Большой скачок времени вызывает интервал один раз, без серии
догоняющих вызовов. Созданный внутри callback таймер ждёт следующего tick.
`wait` возвращает Task; scope отменяет ожидание и прекращает доставку результата.

У обычного `on_world_tick` VC нет аргументов. В шаблоне используется разница
`time.uptime()`; у компонента `on_update(dt)` уже есть delta. Это разные режимы:
выбирайте игровое или реальное время явно. Не вызывайте блокирующие ожидания в
обработчиках кадра. Генераторы также не должны обращаться к сети или миру.

`Task<T>` имеет onDone, onError, cancel и terminal status. Это явная асинхронная
операция, без глобального JS event loop. `sdk/author/network.ts` оборачивает
`network.request` в Task. Отмена прекращает доставку callback; native HTTP-запрос
продолжает выполняться, потому что VC не предоставляет его отмену. Статус HTTP 0
и HTTP-ошибки приходят как HttpResponse, а не как Task rejection. Решение о том,
какой ответ считать успехом, остаётся в вашем коде. Task не является Promise и
не поддерживает `await`; стандартные Promise/async TSTL не проверялись в этой версии.

## Сохранения

`Store<T>` получает путь VC, Schema и defaults. Schema.decode проверяет unknown
и возвращает типизированное значение; encode возвращает сериализуемый VC.Value.
Store проверяет версию, поддерживает явную migrate и отвергает будущие версии.
Ошибка загрузки не заменяет существующий файл defaults. Defaults и snapshot
отделены от live state, чтобы экземпляры не разделяли одну изменяемую таблицу.

Сохраняйте Store в `on_world_save`. Паковый world script загружается ещё до
открытия мира, поэтому создавайте Store с путём `world:` внутри on_world_open.
Store.save использует file.write VC: запись не является транзакцией или атомарной
заменой файла. Для критичных пользовательских данных проект должен отдельно
продумать резервную копию и восстановление. Не записывайте функции, userdata,
сущности и Canvas в JSON; сохраняйте IDs и проверяемые данные.

У компонентов есть штатные ARGS/SAVED_DATA через ComponentContext. Возвращайте
данные из on_save. Фабричный объект один раз копируется в окружение компонента:
позднейшее присваивание полю возвращённого TS-объекта не обновляет его автоматически.
Для изменяемых значений используйте функции/getSnapshot и замыкание.

## Сборка и независимые профили

`units` — независимые TS-программы. headless/world и generator не получают globals
UI/app. Внутри одной unit не включайте сразу все профили ради обхода ошибки.
Разные units могут использовать один pack root, если метаданные пака совпадают;
общие модули должны компилироваться идентично. Помощники TSTL объединяются для пака.

`scripts` поддерживает world/content/hud/block/item. Для block/item часть ID после
двоеточия задаёт имя скрипта; JSON контента должен ссылаться на него штатным способом.
`components`, `generators`, `layouts` генерируют стандартные пути VC. XML, JSON,
TOML, шейдеры и изображения остаются обычными ресурсами в `assets`.
Конфиг не изобретает альтернативный формат контента движка.

В фабрике обязательно пишите `this:void`. Прямые функции engine namespace и
callback вызываются через точку. Методы объектов VC получают self и вызываются
через двоеточие в Lua; декларации этого требуют автоматически. `LuaMultiReturn`
и `$multi` используйте для нескольких native return values, а tuple — для Lua-таблицы.
Координаты пикселей и ID движка не становятся 1-based от TypeScript. TS-массивы
имеют обычные 0-based индексы автора; bytearray остаётся opaque и не является Array.

Ошибку компилятора исправляйте до запуска. Для ошибки исполнения используйте
`vcts explain config.json log.txt`; карта относится к конкретной собранной Lua-версии.
Карты источников не исправляют неизвестные режимы API и не заменяют тест.

## Отложенная загрузка модулей

Если модуль нужен только в обработчике, используйте
`vcts_load<typeof import("pack:module")>("pack:module")` внутри функции.
ID должен быть строковым литералом и разрешаться через `compilerOptions.paths`
или подключённую зависимость. Права межпакового доступа остаются обязательными.
В Lua вызов превращается в штатный `require` без дополнительной обёртки.
Список отложенных зависимостей записывается в `lazyImports` индекса проекта.

Вызывайте функцию после завершения инициализации модуля. Отложенные зависимости
могут быть взаимными; обычные импорты по-прежнему не должны образовывать цикл.

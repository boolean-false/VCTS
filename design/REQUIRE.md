# Загрузка модулей TypeScript в VoxelCore

Адаптер сохраняет штатный `require` VC. Его реализация находится в
`res/scripts/stdmin.lua` движка. Старый transformer из `old/`, заменяющий
вызовы на `load_script`, для новой системы не используется.

## Версии инструментов

7 октября 2026 года npm `latest` для `typescript-to-lua` указывает на 1.37.1.
Эта версия требует ровно TypeScript 6.0.2 через `peerDependencies`; обе версии
зафиксированы в package.json и lockfile. Самая новая отдельная версия TypeScript
не обязательно совместима с последней версией TSTL.

## Правила движка

`require("energy:reservoir")` читает `energy:modules/reservoir.lua`.
`require("energy:devices/battery")` читает
`energy:modules/devices/battery.lua`. В аргумент не добавляются `modules/`
или расширение `.lua`.

Путь без префикса получает имя пака из source вызывающей функции через
`debug.getinfo`. Такой путь считается относительно корня `modules/`, а не
относительно каталога вызывающего файла. Точки не заменяются на разделители
каталогов. При хвостовом вызове сведения о вызывающей функции также могут
отличаться от ожидаемых. Сгенерированные импорты должны использовать явный pack ID.

Модуль выполняется в окружении целевого пака из `__pack_envs`, даже если
его импортировал другой пак. Это важно для глобальных значений пака и `PACK_ID`.
Проверка изолированного загрузчика создаёт эти окружения вручную и не проверяет
порядок их создания реальным загрузчиком контента.

Ключ кеша — полный виртуальный путь, например
`energy:modules/reservoir.lua`. Движок хранит возвращённое значение в
`package.loaded`, а признак выполнения — отдельно. Возврат `nil` тоже кешируется.
Повторный импорт таблицы возвращает ту же таблицу.

Кеш заполняется после выполнения модуля. В проверенной реализации нет отметки
«модуль сейчас загружается»: циклический импорт повторно входит в загрузку.
Сборщик диагностирует циклы runtime-импортов. Импорты только типов
не создают такой зависимости после компиляции.

VC заменяет стандартную таблицу `package` таблицей с `loaded`. Рассчитывать
на обычные Lua `package.path`, `package.searchers` или Node resolution во время
выполнения нельзя. При очистке движок удаляет кеши выгружаемых паков; собственный
параллельный кеш модулей в SDK создавал бы дополнительные обязанности по очистке.

## Несовпадение с выводом транспилятора

Для TypeScript-импорта `./nested/value` TSTL 1.37.1 в проверенном примере
генерирует `require("nested.value")`. VC ищет буквальный файл
`modules/nested.value.lua`, тогда как выходной файл называется `nested/value.lua`.

Адаптер `tools/vc-modules.cjs` сопоставляет разрешённый TypeScript-модуль с владельцем
и путём Lua-файла. Например, публичный импорт `@energy/api` становится
`require("energy:public")`, а импорт внутри `workshop` —
`require("workshop:battery-model")`, если этот модуль содержит runtime-код.
Модуль только с типами в Lua не нужен.

Глобальная замена точек на слеши недостаточна: она не определяет владельца,
не учитывает алиасы и реальные имена файлов. Преобразование использует
`ts.resolveModuleName` и плагин `printer` TSTL. Он переопределяет печать
Lua-вызовов `require`, сохраняя остальные узлы. Имя `value.v1.ts` остаётся
`value.v1.lua`; строковые литералы с текстом, похожим на импорт, не меняются.

Реализация использует `luaTarget: JIT`, отдельные модули без
общего bundle и `luaLibImport: require-minimal`. Набор helper-функций собирается
по `luaLibFeatures` каждого пака. Минимальная библиотека записывается в
`modules/__vcts_lualib.lua`, импортируется с явным префиксом пака и не создаётся,
если она не нужна. Пример `Number.isInteger` проходит проверку загрузчика.
Это не доказывает совместимость всех возможностей стандартной библиотеки.
На границе с VC нужны отдельные декларации: `noImplicitSelf: true` не отменяет
скрытый аргумент `self` у всех методов интерфейсов. Для dot-call функций
и callbacks нативного SDK явно указано `this: void`. Неверный ABI обнаружился
в настоящем движке и теперь покрыт тестом вызова функции обычного Lua из TS.

## Границы первой реализации

Поддерживаются статические импорты, namespace/default/named imports,
реэкспорты, импорты ради побочного эффекта и TypeScript paths. Корни паков
не могут пересекаться. Межпаковый runtime-импорт требует зависимости в
`vc.modules.json` и публичного целевого модуля. Приватность определяется
результатом разрешения файла, поэтому относительный путь не обходит проверку.
Правила относятся к runtime-импортам; отдельной проверки публичности типов пока нет.

Сначала выполняются проверка TypeScript, транспиляция и проверка графа, затем
записываются файлы. При диагностике старый результат остаётся на месте.
Файлы без владельца-пака, коллизии имён выходных файлов без учёта регистра,
циклы и runtime-импорты `.d.ts` без явной реализации отклоняются.

Динамический `import()`, прямые вызовы `require` и сторонние npm runtime-модули
без владельца пока не поддерживаются. Обычный Lua подключается явно:

```json
"nativeModules": [
  { "id": "vcts:core", "declaration": "../design/contracts/core.d.ts", "source": "../runtime/core.lua" }
]
```

Пути заданы относительно `vc.modules.json`. Исходный Lua копируется в
`vcts/modules/core.lua`, а разрешившийся в указанную декларацию TS-импорт
превращается в `require("vcts:core")`. Для другого пака нужны зависимость `vcts`
и публичный модуль `core.lua`. Проверяются коллизии с TS-выводом и другими
нативными модулями, включая различие только регистром. Внутренние импорты Lua
не анализируются: такой модуль — непрозрачная вершина графа. Его циклы,
правильность деклараций и вызовов требуют интеграционной проверки.
Молчаливого предположения, что `.d.ts` означает готовую реализацию, нет.
Спецификатор `lualib_bundle` и имя корневого модуля `__vcts_lualib` зарезервированы.

Конфигурация сборки сейчас отдельная JSON, а `design/project.ts` остаётся эскизом
будущей авторской конфигурации. Адаптер выводит только модули. Отдельный
`tools/build-demo.cjs` использует его для сборки полного демо: создаёт package.json,
project.toml, описания блоков и скрипты событий, копирует общий XML панели.
Source maps и отображение ошибок в исходный TypeScript пока не подключены.
Обновление TSTL требует повторного запуска тестов: генерация helper-библиотеки
использует внутренний модуль закреплённой версии TSTL.

## Проверка

`tools/check-vc-loader.cjs` извлекает фактические `parse_path`, `require` и
`__load_script` из локального исходника движка. Неожиданное изменение границ
этих фрагментов останавливает проверку. Файловый API заменён таблицей в памяти.
Сама игра, регистрация паков и очистка при выходе из мира в эту проверку не входят.

Проверено: исходный импорт TSTL не разрешается; явный путь VC работает;
Lua-вспомогательная библиотека загружается; краткий импорт выбирает пак вызывающего
скрипта; межпаковый импорт выполняется в окружении целевого пака; обычный и nil
результаты кешируются; циклическая загрузка повторно входит в модуль.

В старом диагностическом `check-vc-loader.cjs` один импорт заменяется на заранее
известный путь для сравнения двух вариантов. Основные тесты
`tools/tests/vc-modules.test.cjs` исполняют уже настоящий вывод адаптера без
подмены импортов. Они проверяют относительные пути, aliases, reexports,
импорт только типов, окружения, общий объект через кеш, побочные эффекты,
отрицательные сценарии и защиту сгенерированных файлов от перезаписи ручных правок.

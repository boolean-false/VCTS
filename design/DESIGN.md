# Авторский код для проектов VoxelCore

Первый сценарий — накопитель с сохраняемым зарядом, панелью управления и
отложенной зарядкой. Пак `energy` предоставляет библиотеку, а `workshop`
использует её публичный интерфейс. Их объединяет отдельный проект VC.
Такой пример проверяет границы паков, состояния и интерфейса без привязки
системы разработки к устройству конкретной игры.

Контракты остаются экспериментальными, но сценарий уже собирается в отдельный
проект и проходит headless-проверки внутри VC. В `runtime/core.lua` реализованы
поля, экземпляры блоков, подписки и планировщик. Генератор демо создаёт JSON
контента и входные скрипты событий. Графическое отображение панели пока не
прошло проверку; модель UI и её обновления проверены отдельно без окна.

## Что пишет автор

Автор библиотеки пишет обычные функции и явно экспортирует публичный API.
Потребитель импортирует `@energy/api`; ему достаточно знать `Reservoir`,
`Transfer`, `restore` и `transfer`. Внутреннее размещение функций можно менять,
сохраняя публичный контракт. Это сокращает необходимый контекст, но не устраняет
необходимость понимать смысл операций и проверять поведение.

Автор устройства описывает сохраняемые поля один раз и получает их типы
в обработчике. Отдельная фабрика создаёт временное состояние каждого загруженного
экземпляра. Явный список блоков в `pack.ts` заменяет регистрацию через побочные
эффекты импорта. Определение блока при импорте не должно запускать игровую работу.

Автор UI получает снимок состояния и команды. Он не импортирует реализацию
блока и не записывает значения в сохранение напрямую. UI может измениться
без изменения формата сохраняемых полей.

## Поведение накопителя

Вместимость составляет 100 единиц. Кнопка зарядки добавляет 10 единиц через
две секунды; кнопка использования сразу расходует 10. Повторный запуск зарядки
и разрядка во время ожидания запрещены самим обработчиком, даже если кнопку
вызвали программно. Перед записью повторно проверяется текущее количество энергии.

Пример не списывает ресурсы и не моделирует реальный источник энергии. Он
показывает отложенное действие и его владельца; это не экономическая модель игры.
`after` выполняет callbacks синхронно из `on_world_tick`, считая 20 тиков
одной секундой. Когда мировые тики остановлены, задержка не продвигается.
Перед вызовом задача удаляется из очереди. Ошибка callback передаётся движку;
отдельной политики восстановления после ошибок пока нет.

| Данные или работа | Владелец | Поведение |
| --- | --- | --- |
| Количество энергии | Сохраняемое поле блока | Сохраняется средствами VC |
| Флаг зарядки и сообщение | Загруженный экземпляр блока | При выгрузке отбрасываются |
| Отложенное пополнение | Lifetime экземпляра блока | При закрытии владельца отменяется |
| Подписка открытой панели | Экземпляр панели | При закрытии панели освобождается |

Закрытие панели не отменяет зарядку. Удаление, замена или выгрузка блока
отменяет ещё не начавшийся callback и закрывает его панели. При повторной
загрузке сохранённая энергия остаётся, зарядка не возобновляется. Выход из мира
освобождает всех владельцев. Блок по тем же координатам после замены должен
иметь новый lifetime: одной проверки координат для защиты от старого callback
недостаточно.

Адаптер учитывает экземпляры отдельно, поскольку обычные скрипты блоков VC
исполняются в окружении пака. Сгенерированные обработчики размещения, удаления,
замены и присутствия управляют lifetime; каждый тик дополнительно проверяет,
что блок ещё загружен. Headless-тест использует реальные `block.place`,
`block.destruct` и перемещение игрока для выгрузки чанков. Отложенный
`blockpresent` после закрытия мира игнорируется. Повторная регистрация той же
таблицы определения допустима: VC может сохранить кеш `require` между мирами.

Важно для совместимости с Lua: низкоуровневый `block.set` обходит события
размещения. Замену блока тем же ID между двумя тиками адаптер не обнаружит,
если операция не породила lifecycle-событий. Для управляемых блоков нужны
`block.place`/`block.destruct` либо явное согласование с адаптером.

## Что проверяет TypeScript

Проверка отклоняет строку вместо числового количества, доступ к успешному
результату без разбора варианта, опечатку в поле UI, запись в снимок UI,
неверные аргументы команды и неверные обращения к сохраняемым полям блока.
Типы сохраняемого состояния выводятся из `field.int16`, а не объявляются повторно.

Она пока не проверяет существование текстуры, уникальность content ID
или допустимый диапазон каждого `number`. Зависимости runtime-импортов
проверяет отдельный сборщик.
Часть этих проверок должна стать работой сборщика; внешние значения и записи
в поля требуют runtime-валидации. `restore` явно проверяет целые значения
и диапазон загружаемого состояния. Для повреждённого сохранения нужна отдельно
согласованная политика восстановления; здесь неверное значение даёт ошибку.

Путь `@energy/api` сейчас настроен через TypeScript paths. Это ещё не менеджер
пакетов и не запрет импортировать чужую реализацию относительным путём.
В адаптере импортов проверяются runtime-границы и зависимости через
`vc.modules.json`, в том числе при сборке SDK-образца. Разрешение версий
и публичность типов остаются отдельными задачами.

## Сопоставление с VoxelCore

| Авторский элемент | Предполагаемый результат сборки |
| --- | --- |
| `project.ts` | `project.toml`, состав content и конфигурация запуска |
| `pack.ts` | `package.json` и явно перечисленные определения контента |
| Библиотечный модуль | Lua-модуль, совместимый с `require` VC |
| `defineBlock` | JSON блока и Lua-обработчики событий |
| `field.int16` | Описание поля JSON и доступ через API полей VC |
| `definePanel` | XML-макет, обработчики и обновление состояния панели |
| `Lifetime.after` | Отложенный callback с учётом владельца |

Стандартные контент-индексы `content.json` должны оставаться под управлением
механизмов VC, без самостоятельного переназначения ID сборщиком.

В библиотеке используются обычные TypeScript-функции. Этот сценарий проверен
с TypeScriptToLua 1.37.1 в реальном LuaJIT VC; это не доказывает совместимость
всех возможностей TypeScript. На границе с Lua методы и callbacks объявлены
с `this: void`: одного `noImplicitSelf` оказалось недостаточно. Без явного
контракта TSTL добавлял `self` к вызову `field.int16`. Подробности в REQUIRE.md.

Генератор демо вычисляет доверенные TS-определения в Node с SDK для сбора
метаданных. Игровые handlers и transient-фабрики при этом не вызываются.
Это не песочница для чужого кода. Пока генератор предназначен для данного
сценария: состав проекта, подпись блока и макет панели заданы для демо.

## Предлагаемые решения и открытые вопросы

Начальный приоритет — небольшая типизированная привязка к VC, явные модули,
обычный Lua на выходе и возможность подключать существующий Lua-код. Пример
не требует глобального контейнера сервисов, наследования от базового класса
или автоматического обнаружения всех файлов.

TS-описание панели выбрано для компактного сравнения типов. Оно не закрепляет
отказ от XML. Второй вариант — XML как исходник и генерируемые типы элементов
и обработчиков. Перед выбором нужно сравнить оба на более сложном интерфейсе.

В примере сохраняется одно числовое поле. Изменение его имени или формата
потребует правил миграции сохранений независимо от результата typecheck.
Также пока не спроектированы компоненты сущностей с `SAVED_DATA`, генераторы,
проектные скрипты и полный прямой доступ к API движка. Для обычного Lua добавлено
явное сопоставление `.d.ts` с исходным Lua-модулем в `nativeModules`.
Для них нужны отдельные небольшие примеры, прежде чем объявлять SDK универсальным.

## Как оценивать изменения

| Изменение | Ожидаемая обратная связь |
| --- | --- |
| Переименовать `BatteryView.stored` | Компилятор указывает производителя снимка и обращения UI |
| Переименовать сохраняемое поле | Компилятор указывает обращения; миграция данных остаётся отдельной задачей |
| Изменить аргумент публичной функции | Компилятор указывает несовместимые вызовы потребителей |
| Изменить внутренний алгоритм энергии | Публичный API может остаться прежним; нужны поведенческие проверки |
| Закрыть мир во время зарядки | Проверяется только адаптером и интеграционным запуском |

Сравнение с Lua должно использовать ту же структуру модулей и хорошие аннотации,
иначе результат смешает пользу языка с пользой организации проекта. Для задач
человека и нейросети стоит учитывать число прочитанных файлов, объём контекста,
время исправления и оставшиеся ошибки. Краткость исходника сама по себе не
доказывает удобство.

## Результат первой проверки

`npm run check` проходит на TypeScript 5.9.3, включая семь отрицательных примеров.
При переименовании `BatteryView.stored` в `energy` в отдельной временной копии
компилятор указал создание снимка в `battery.ts` и три обращения в
`battery-panel.ts`. Исходный образец сохранён без этого переименования.
Это подтверждает обнаружение структурного изменения контракта в данном примере;
влияние на удобство больших проектов и качество работы нейросети ещё не измерено.

После подключения актуального TypeScriptToLua проверка повторно проходит на
TypeScript 6.0.2, требуемом TSTL 1.37.1. Устаревший `baseUrl` удалён, алиасы
разрешаются относительно файла конфигурации.
